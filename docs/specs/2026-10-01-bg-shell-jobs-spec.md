# Спека: bg-jobs — фоновые shell-джобы для pi

- **Статус:** черновик (восстановлено 2026-10-01 после затирания установленной
  копии `pi update --extensions`; канонический экземпляр — этот репозиторий)
- **Дата:** 2026-10-01
- **Автор идеи:** Ivan Sinyavskiy (stargot)
- **Режим:** spec (задание на реализацию нового расширения в `stargot/pi-extensions`)
- **База:** пакет 0.7.0, Node ≥ 22.19.0, pi ≥ 1.0.0
- **Источник вдохновения:** контур `process` пакета
  [pi-background-tasks](https://www.npmjs.com/package/pi-background-tasks) 2.6.9
  (`bg_run`/`/bg`/dock/уведомления), урезанный до нужного и переложенный на
  конвенции этого репозитория (Windows 11 + pwsh, biome, `node --test`).

---

## 1. Резюме (TL;DR)

Новое расширение `bg-jobs`: долгие шелл-команды (dev-серверы, watch'и, миграции,
длинные тесты) запускаются в фоне и не блокируют ход сессии. Модель и пользователь
получают: мгновенный возврат `id` + пути к output-файлу, durable-лог на диске,
уведомление о терминальном состоянии и (для модельных запусков) follow-up ход с
кратким хвостом вывода. Управление — четырьмя инструментами (`bg_run`, `bg_status`,
`bg_logs`, `bg_kill`), командами (`/bg`, `/jobs`, `/logs`, `/kill`) и компактным
виджетом у редактора. Песочницы нет: команды исполняются с правами пользователя,
это фиксируется в описании тула и README.

Объём: ~400–600 строк без тестов. Один новый каталог `extensions/bg-jobs/`
(+ выделение общего модуля kill-дерева в `extensions/shared/`), одна строка в
`package.json`.

## 2. Проблема и контекст

**Текущая ситуация.** В pi есть три способа исполнить шелл-команду, и все для
долгих задач плохи:

| Способ | Поведение | Проблема для длинных задач |
|---|---|---|
| `pi.bash` модели | Блокирующий вызов | Ход висит, пока не завершится; таймауты pi режут вывод |
| Терминал вне pi | Пользователь руками | Нет связи с сессией: модель не знает статус, результат надо переносить руками |
| `subagents` (свой пакет) | Панель WezTerm/herdr | Заточен под *агентов* (pi-процессы), а не под сырые команды; панель под dev-сервер — расход поверхности без пользы |

**Типовые кейсы, которые сейчас делаются плохо:**

1. `npm run dev` / `npm run watch` на время рефакторинга — нужны живыми, пока
   модель правит код, и никого не блокировать.
2. Длинная проверка (`pnpm test`, линтер по всему репо, сборка) — модель сейчас
   либо ждёт, либо «засыпает» polling-циклами.
3. Migration dry-run / сиды / генераторы — запустить, забыть, узнать результат,
   когда он понадобится.

**Почему не pi-background-tasks:** пакет хороший, но из 5 фичевых контуров
(process / delegate / fusion / attested / attribution) нужен только `process`;
delegate пересекается с собственным `subagents`, fusion требует Anthropic/Codex
OAuth (стек сидит на zai/GLM), attribution бесполезен вне Anthropic. Тащить 11
тулов ради 4 — плохой обмен веса tool-схем на пользу. Собственное расширение
ложится в существующие конвенции пакета и стоит ~0 зависимости.

## 3. Цели и анти-цели

### Цели

- **Не блокировать ход.** `bg_run` возвращает управление сразу: `{ id, outputPath }`.
- **Durable-вывод.** Полный stdout/stderr пишется в файл на диске; модель читает
  ограниченный хвост с маркером усечения и путём к полному логу.
- **Доставка терминального состояния.** Running-джобы уведомляют о завершении:
  пользователь — тостом, модель — новым ходом с кратким итогом (exit code + хвост).
- **Управление из диалога и с клавиатуры.** Одинаковые операции доступны модели
  (инструменты) и пользователю (команды): запуск, статус, логи, убийство.
- **Переживать `/reload`.** Процессы не привязаны к рантайму расширения: реестр на
  диске, процессы детачатся; после reload реестр подхватывается по PID.
- **Windows-first.** Убийство дерева процессов через Job Object (выделить из
  `subagents/proctree.ts` в `extensions/shared/`), шелл — pwsh.
- **Видимость.** Компактный виджет `ctx.ui.setWidget()` (кол-во running + свежие
  терминальные события) и записи в session-trace (`session-trace:bg-jobs`).

### Анти-цели (не делаем)

- ❌ Делегирование инспекций модели-ребёнку — это `subagents`.
- ❌ Fusion / мульти-модельные сравнения — нет Anthropic/Codex OAuth в стеке.
- ❌ Anthropic attribution / cache policy — вне zai/GLM.
- ❌ Sandbox — не берёмся изолировать команды; честно документируем.
- ❌ Межпроцессный mesh/EventBus для чужих расширений — можно добавить позже,
  если появится второй потребитель реестра.

## 4. Предлагаемое решение

### 4.1 Архитектура

```
модель ── bg_run ──┐                     пользователь ── /bg ──┐
                   ▼                                            ▼
            ┌─────────────── Registry (.pi/jobs/jobs.json) ◄────┐
            │  id → {command, pid, status, outputPath, …}       │
            └───────┬───────────────────────────────────────────┘
                    │ spawn (detached, pwsh, stdout→file)
                    ▼
            Runner: процесс ОС (Job Object) + watcher (тик 1 c)
                    │                                 │
                    ▼ терминальное состояние          ▼ хвост лога
            notify (пользователь)          follow-up ход (модель)
                    └────────────┬────────────────────────┘
                                 ▼
                 widget (setWidget) + session-trace артефакт
```

Ключевой принцип: **рантайм расширения — не владелец процессов**. Runner спавнит
процесс detached, пишет всё состояние в реестр на диске и держит watcher на тике.
Любой компонент (после reload, после краша watcher'а) восстанавливает картину из
реестра + PID-проверки. Сессия умирает — по умолчанию `session_shutdown` убивает
живые джобы (идемпотентно), при `surviveExit: true` — оставляет сиротами с записью PID.

### 4.2 Решения (ADR-lite)

**ADR-1: своё расширение vs pi-background-tasks с `PI_BG_FEATURES=process`.**
Контекст: нужен только process-контур; стек — свой пакет с жёсткими конвенциями
(Windows/pwsh, biome, `node --test`, README на каждое расширение). Варианты:
(а) ставить готовый пакет, (б) писать своё. Выбор: **(б)**. Обоснование: 4 тула
против 11; готовый пакет не знает про session-trace/пакетные конвенции; своя
реализация ~500 строк и полностью под контролем; зависимость исчезает из
`~/.pi/agent`. Последствия: свой maintenance; компенсируется тестами и малой
поверхностью.

**ADR-2: отдельное расширение vs модуль внутри `subagents`.**
Контекст: `subagents` уже умеет процессы, панели, вотчеры, steer-доставку; в пакете
есть конвенция `extensions/shared/` для модулей, нужных нескольким расширениям.
Варианты: (а) расширить `subagents` режимом «сырых джобов», (б) отдельное
расширение. Выбор: **(б)**, а общий низкоуровневый код — вынести: kill дерева
процессов из `subagents/proctree.ts` переезжает в `extensions/shared/proctree.ts`,
`subagents` и `bg-jobs` потребляют его оттуда. Обоснование: разный объект владения
(агент-сессия vs сырой процесс), разная поверхность (панель vs без панели), разный
жизненный цикл (смерть сессии vs переживание reload/exit); дублировать kill-логику
в двух местах не нужно — shared для того и заведён. Последствия: небольшая
механическая правка импортов в `subagents`; обе стороны обязаны не тянуть в shared
панельную/сессионную специфику.

**ADR-3: реестр и артефакты — в проекте, `.pi/jobs/`.**
Контекст: джобы принадлежат проекту, но не должны попадать в git; состояние
нужно переживать reload и читать из CLI/тестов. Выбор: `.pi/jobs/jobs.json`
(атомарная запись tmp+rename) + `.pi/jobs/<id>/output.log`; каталог исключается
через `.git/info/exclude` при первом запуске (как делают worktree-реестры
pi-fabric), не трогая пользовательский `.gitignore`. Альтернативы: `~/.pi/agent/...`
(глобально — плохо: разные проекты, пересечение id), `pi.appendEntry()`
(сессия-скоуп — не переживает корректно смену ветки/сессии, а джобы живут дольше).
Последствия: нужен lock/merge при записи (stale-safe, запись только своих полей —
по образцу `actors.json` из pi-fabric); компенсируется одним модулем `registry.ts`.

**ADR-4: доставка завершения — notify+wake для модельных, notify-only для
пользовательских.**
Контекст: джоб, запущенный моделью через `bg_run`, — часть её задачи: модель должна
узнать результат; джоб из `/bg` — фоновая мебель пользователя. Выбор: повторить
политику pi-background-tasks — `bg_run` по умолчанию будит модель follow-up ходом
(тот же механизм доставки итога, что у `subagents`: steer/новый ход, краткий хвост
≤ 2К символов + exit code + путь к полному логу); `/bg` — только `ctx.ui.notify`.
Опция `wake: false` у `bg_run` переводит джоб в notify-only. Последствия:
нужен антиспам-контур: не будить модель повторно, если ход уже начат другим
событием — доставлять факты в ход, который всё равно случился.

**ADR-5: без песочницы, но с явным пассом ответственности.**
Контекст: изолировать произвольные шелл-команды — отдельная большая задача; ни
pi, ни pi-background-tasks её для shell-джобов не решают. Выбор: запуск с правами
пользователя; в `description` тула для модели и в README — прямым текстом
«команда исполняется как локальный процесс с вашими правами и доступами».
Последствия: модель может запустить что угодно — как и через обычный bash-тул pi;
затягивание аппрувлов не входит в скоуп (см. открытые вопросы).

**ADR-6: переживание reload — да; переживание выхода pi — opt-in.**
Контекст: `/reload` заменяет рантайм расширения, но процесс pi жив; выход pi
убьёт детей только если они в его Job Object. Выбор: процессы спавнятся как
обычные дети без Job Object — на Windows дети переживают выход родителя и так,
а Job Object требует нативного кода и держащего handle, конфликтующего с
переживанием reload. Kill дерева — `taskkill /T /F` (общий
`extensions/shared/proctree.ts`, тот же механизм, что у subagents). Reload
подхватывает реестр по PID — джобы живут.

Отклонение 1 от черновика: kill дерева делается `taskkill /T /F` вместо
Job Object — дрейф цепочек cmd/npm (внучатый процесс, переживший kill
родителя) — принятый риск v1; см. §6. Перед `taskkill` сверяется имя образа
процесса (`Get-CimInstance`, ожидаем pwsh) — защита от удара по чужому дереву
после переиспользованного PID.

Отклонение 2 от черновика: `session_shutdown` убивает running-джобы только при
`reason === "quit"`; при reload/new/resume/fork джобы переживают — новый
`session_start` подхватывает реестр по PID. Это снимает противоречие черновика
ADR-6 («kill всех running на любой shutdown») с §3 и §4.6, где /reload явно
обязан джобы сохранять (набор reasons — по types.d.ts pi 1.0.0).

При `session_shutdown(quit)`: kill всех running, при `surviveExit: true`
(флаг `--survive-exit` у `/bg`) — оставить работать, пометить `orphaned` с
записью PID/времени. Последствия: kill при выходе — защита от расползающихся
dev-серверов; сироты разбираются при следующем `session_start` того же
проекта: running с мёртвым PID → `orphaned`; `orphaned` с живым pwsh-PID
воскресает в `running` (watcher подхватывает PID-опросом), delivery — только
notify при смене сессии.

### 4.3 Модель данных

```jsonc
// .pi/jobs/jobs.json
{
  "version": 1,
  "jobs": {
    "b12ab34c": {
      "id": "b12ab34c",              // 8 hex, локально уникальный
      "name": "Typecheck watch",
      "command": "npm run typecheck -- --watch",
      "cwd": "<abs path>",
      "shell": "pwsh",
      "pid": 12345,                   // после спавна
      "status": "running",            // running|completed|failed|timeout|killed|orphaned
      "exitCode": null,
      "startedAt": "2026-10-01T12:00:00Z",
      "endedAt": null,
      "outputPath": ".pi/jobs/b12ab34c/output.log",
      "origin": "model",              // model | user
      "wake": true,                   // будить модель по завершении
      "timeoutSeconds": null,
      "sessionId": "<pi session id>",
      "surviveExit": false
    }
  }
}
```

Артефакты: `.pi/jobs/<id>/output.log` — единственный артефакт; ротации нет,
размер ограничивает сам пользователь командой (при переполнении диска — не наша
проблема v1; см. открытые вопросы про cap).

### 4.4 API

**Инструменты** (TypeBox-схемы, `details` — структурированное состояние для рендера):

| Тул | Вход | Выход / поведение |
|---|---|---|
| `bg_run` | `name`, `command`, `cwd?`, `timeoutSeconds?`, `wake?` (default true), `surviveExit?` | Сразу: `{ id, outputPath, pid? }`. Спавн detached, watcher стартует. Модельный origin |
| `bg_status` | `id?` (нет id → все) | Список: `{ id, name, status, startedAt, endedAt?, exitCode?, outputPath }` |
| `bg_logs` | `id`, `tailChars?` (default 4096, max 65536) | Хвост лога + `{ truncated, outputPath, totalChars }`; маркер усечения в `content` |
| `bg_kill` | `id` | Kill дерева процессов (Job Object), статус → `killed` |

Все тула — `direct`-exposure; `bg_run`/`bg_kill` — `destructiveHint: true`
(честная подсказка аппрувал-экстеншенам). Ошибки (нет такого id, уже завершён) —
броском с внятным текстом и списком живых id.

**Команды** (пользовательский origin, wake=false всегда):

| Команда | Поведение |
|---|---|
| `/bg <name> :: <command>` или `/bg <command>` | Запуск; `--survive-exit` одним ведущим флагом; ответ — id + путь |
| `/jobs` | Таблица джобов (id, статус, имя, elapsed) в диалоге |
| `/logs <id> [chars]` | Хвост лога в диалог |
| `/kill <id>` | Kill с подтверждением `ctx.ui.confirm` |

**UI:**

- Виджет `ctx.ui.setWidget()`: `bg 2 running · 1 done` — только когда есть живые
  или непросмотренные терминальные события; клик/команда не обязательны (v1
  без интерактивного dock — см. открытые вопросы).
- `ctx.ui.notify` на терминальные события пользовательских джобов.
- Guard `ctx.mode === "tui"` для всего UI; в RPC/print/JSON режимах — только
  инструменты и файлы.

**Интеграции со стеком:**

- `session-trace`: кастомная запись `session-trace:bg-jobs` (id, имя, статус,
  длительность, exit code) — по образцу `session-trace:subagents` в subagents.
- `session-ledger`: v1 не трогаем (джобы не жгут токены).
- Другие расширения: read-only доступ к реестру — обычный импорт модуля не даём;
  при появлении потребителя добавим каналы `pi.events` (аналог EventBus
  pi-background-tasks). Сейчас — анти-цель.

### 4.5 Структура файлов

```

└── test/
    └── proctree.test.ts   # тесты переезжают вместе с модулем

├── README.md          # по конвенции пакета: таблица, как работает, ограничения
├── index.ts           # фабрика: регистрация тулов, команд, widget, session-хуков
├── registry.ts        # jobs.json: load/save (tmp+rename), stale-safe merge, id-генерация
├── runner.ts          # spawn (pwsh, detached, Job Object), watcher-тик, таймауты

    ├── registry.test.ts

```

Регистрация: строка `./extensions/bg-jobs/index.ts` в `"pi".extensions` пакета;
строка в таблице README пакета. `npm run check` — зелёный (biome + tsc + tests),
`npm run smoke` грузит расширение. Вынос `shared/proctree.ts` не должен менять
поведение `subagents` — его тесты остаются зелёными без правок сценариев.

### 4.6 Поведение в жизненном цикле pi

- **Фабрика** — ничего не спавнит и не читает диск сверх импортов (контракт pi:
  некоторые вызовы грузят расширения без сессии).
- **`session_start`** — подхват реестра: PID-проверка running-джобов
  (мёртв PID без записи `endedAt` → `orphaned`), старт watcher'а, монтаж виджета.
- **`session_shutdown`** — идемпотентный kill (кроме `surviveExit`), финальная
  запись реестра, снятие виджета.
- **Reload** — новый экземпляр проходит тот же `session_start`; старый watcher
  умирает вместе с рантаймом, состояние теряется только на тик.
- **Параллельные tool-вызовы** — `bg_run` из одного ассистентского сообщения
  (два параллельных вызова): реестр через общую очередь записи (мьютекс модуля),
  id генерируются до спавна; коллизия невозможна.

## 5. Альтернативы (отклонённые)

| Альтернатива | Почему нет |
|---|---|
| **pi-background-tasks с `PI_BG_FEATURES=process`** | Рассматривалась как план Б (см. ADR-1): лишние 7 тулов в схеме даже с флагом не исчезают совсем — disabled-контуры всё равно грузят entrypoints; нет интеграций со стеком; чужой maintenance-цикл обновлений |
| **Расширение `subagents` режимом raw-jobs** | Смешивает жизненные циклы и поверхность (ADR-2) |
| **Обычный `bash cmd &` через тул pi** | Нет реестра, нет durable-логов, нет уведомлений, процесс-сирота без PID-учёта; model-facing вывод мгновенно замусоривается |
| **Отдельный npm-пакет (не внутри pi-extensions)** | Излишне: расширение приватное, пакет уже приватный (`private: true`); отдельный пакет = отдельный релизный цикл без выгоды |

## 6. Риски и смягчение

| Риск | Вероятность | Урон | Смягчение |
|---|---|---|---|
| Расползающиеся процессы: пользователь забыл про 5 dev-серверов | Высокая | Средний: порты, память | kill по умолчанию при shutdown; `/jobs` показывает elapsed; `/kill` в один шаг |
| Модель плодит джобы вместо честного ожидания (анти-паттерн polling через bg) | Средняя | Средний: шум, цена | `bg_run` с `wake: true` возвращает модель только по факту завершения; описание тула прямо запрещает sleep-петли |
| Kill не убивает всё дерево (внучатые процессы, npm-обёртки) | Средняя (Windows) | Средний: сироты на портах | Килл дерева — `taskkill /T /F` вместо Job Object: дрейф цепочек cmd/npm — принятый риск v1 (ADR-6, отклонение 1); Job Object требует нативного кода/держащего handle, конфликтующего с переживанием reload. Проверенный `shared/proctree.ts` + guard переиспользованного PID (сверка имени образа перед kill); POSIX — процесс-группа + `SIGKILL` |
| Регрессия `subagents` при выносе proctree в shared | Низкая | Средний: сломан существующий пакет | чисто механический переезд + его тесты переезжают вместе; `npm run check` зелёный на обоих потребителях |
| Гонки реестра при параллельных вызовах/крashе записи | Низкая | Низкий: потеря одной записи | tmp+rename (атомарная замена), merge только своих полей, id до спавна |
| Бесконечный лог съедает диск | Низкая | Средний | v1: документируем; v2 (опционально): cap размера с усечением головы |
| Wake-ход приходит в неудачный момент (пользователь печатает) | Низкая | Низкий | follow-up как у subagents: очередь pi сама вставит ход; при незавершённом вводе — notification-only |
| Нечитаемый вывод на не-UTF8 командах (Windows-кодировки) | Средняя | Низкий: кракозябры в хвосте | `chcp 65001`/`[Console]::OutputEncoding` в pwsh-обёртке; fallback — полный лог в файле |

## 7. Открытые вопросы

1. **Аппрувалы.** Должен ли `bg_run` модели требовать подтверждения пользователя
   в TUI (как опасные тулы), или доверяем существующей политике bash-аппрувлов pi?
   Склоняемся ко второму + `destructiveHint`, но решить перед реализацией.
2. **Интерактивный dock.** Виджет v1 — пассивная строка. Нужен ли полноценный
   dock с навигацией (как footer dock pi-background-tasks) или хватит `/jobs`?
   Отложить до первого ощущения неудобства.
3. **Cap лога.** Вводить ли сразу усечение головы при > 10 МБ, или честно
   документировать «следи за размером»?
4. **Кросс-платформенность.** POSIX-ветка (процесс-группы) — писать сразу или
   Windows-first с `TODO(posix)` в `shared/proctree.ts`? Пакет в целом
   Windows-first, но тесты в CI должны остаться зелёными на любой машине разработки.
5. **Имя.** `bg-jobs` vs `bg-tasks` vs `jobs`. Внутрипакетный префикс команд
   `/bg*` свободен, конфликтов поверхностей с pi-background-tasks не будет —
   оба не стоят одновременно.

## 8. Критерии готовности

- [ ] `bg_run` возвращает `{ id, outputPath }` < 500 мс, команда исполняется
      detached и переживает завершение вызвавшего хода
- [ ] Терминальное состояние модельного джоба доставляет follow-up ход
      (exit code + хвост ≤ 2К + путь), пользовательского — notify
- [ ] `bg_logs` отдаёт хвост с честным маркером усечения и путём к полному логу
- [ ] `bg_kill` убивает дерево процессов на Windows (проверено на npm-обёртке:
      `npm run dev` → kill → порт свободен)
- [ ] `shared/proctree.ts` выделен, `subagents` потребляет его без поведенческих
      изменений (тесты subagents зелёные без правок)
- [ ] `/reload` не убивает running-джобы; после reload реестр подхвачен,
      статусы корректны
- [ ] Выход pi без `surviveExit` убивает джобы; с `surviveExit` — оставляет
      working-сироту с пометкой `orphaned` при следующем старте
- [ ] Виджет появляется при ≥ 1 running и исчезает после прочтения всех
      терминальных событий
- [ ] RPC/print/JSON режимы работают без UI-путей (guard `ctx.mode`)
- [ ] `npm run check` и `npm run smoke` зелёные; тесты покрывают registry
      (гонки/merge), runner (фикстуры sleep/echo/exit-code), format
- [ ] README расширения и строка в README пакета; в описаниях тулов зафиксировано
      отсутствие песочницы
