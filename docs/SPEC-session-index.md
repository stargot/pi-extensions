# SPEC: Общий индекс сессий (`shared/session-index.ts`)

Статус: черновик v1 · Источник: RESEARCH.md §1.3 (+§4#5), фидбек «consolidate висит минутами»
Дата: 2026-09-25

## Проблема

Три потребителя читают сессии JSONL по-своему и все — с полным перечитыванием:

| Потребитель | Сегодня | Боль |
|---|---|---|
| session-ledger (`/stats`) | `loadSessions()` перечитывает **все** файлы при каждом вызове | `/stats` и CLI тормозят пропорционально истории |
| session-recall (`/recall`) | инкрементальный кэш `IndexCache` (mtime+size) **в памяти процесса** | полный рескан на каждом старте pi |
| session-trace | читает один файл по требованию | — (не потребитель v1) |

## Цели

1. Персистентный инкрементальный кэш разбора: файл разбирается один раз, повторные вызовы
   читают кэш; перечитываются только новые/изменившиеся файлы.
2. Один проход парсера кормит **оба** представления: units (поиск) и summary (агрегаты).
3. Потребители сохраняют свои публичные API — индекс живёт в `shared/`, расширения
   переключаются на него точечно.
4. Ранжирование recall: BM25-подобный скор вместо чистого фильтра.

## Не-цели (v1)

- trace не переводится на индекс (его разовое чтение одного файла — другой сценарий).
- Демон-процесс/фоновая индексация: обновление ленивое, при вызове потребителя.
- Полнотекстовый движок: свой подсчёт тф/idf, без зависимостей.

## Дизайн

### Хранение

Один JSON: `~/.pi/agent/cache/session-index.json`

```jsonc
{
  "version": 1,
  "files": {
    "/abs/path/session.jsonl": {
      "mtimeMs": 1730000000000, "size": 123456,
      "summary": { /* SessionSummary как в ledger */ },
      "units": [ /* Unit как в recall, text обрезан до 4KB */ ]
    }
  }
}
```

- Инвалидация: `version` не совпал или JSON бит → полный ребилд (один раз, не каждый старт).
- **Кап текста юнита в кэше 4КБ**: сниппеты recall ~120 символов, полный текст всегда остаётся
  в самом jsonl. Ограничивает рост кэша (главный риск формата «один JSON»).
- Запись атомарная (tmp + rename), уникальное имя tmp (урок running-index).
- Чтение при старте потребителя: один JSON вместо парсинга сотен jsonl.

### API (`shared/session-index.ts`, чистый модуль без pi-runtime)

```
type SessionFileRecord = { mtimeMs, size, summary: SessionSummary, units: Unit[] }
type SessionIndexData  = { version: 1, files: Record<string, SessionFileRecord> }

loadIndex(path): SessionIndexData            // битый/старый → {version:1, files:{}}
saveIndex(path, data): void                  // атомарно
refreshSharedIndex(root, data, opts): { changed: number, files: number }
  // discoverSessionFiles → для каждого: mtime+size изменились? → один проход
  // parseFileUnitsAndSummary() → обновить запись; пропавшие файлы удаляются
```

- Парсер «один проход — два представления»: объединяет логику `recall/search.ts`
  (`parseUnits`) и `ledger/ledger.ts` (`loadSessions`) в общий обход записей.
  Оба текущих парсера остаются как тонкие обёртки над общим обходом (совместимость тестов).
- Расхождение парсеров — известный риск: ledger считает compaction/branch_summary и
  tool-calls без текста, recall их пропускает. Обход обязан покрыть надмножество случаев;
  эквивалентность проверяется тестом-сравнением на фикстурах (золотые файлы обоих парсеров).

### Потребители

- **session-ledger**: `loadSessions(files)` → `loadSessionsFromIndex(root, index)`;
  `/stats` и CLI читают только кэш + изменившиеся файлы.
- **session-recall**: `IndexCache` заменяется на `SessionIndexData` (персистентный);
  `refreshIndex` → `refreshSharedIndex`; плюс ранжирование.
- **подключение**: ленивое, в момент команды; файл блокируется на время записи
  (tmp+rename — гонки между процессами остаются last-writer-wins, как в running-index).

### Ранжирование recall (BM25-lite)

`score = Σ tf(term)·idf(term) · recency`, где tf — число вхождений в unit.text,
idf — по коллекции units текущего индекса, recency — множитель 1.0 → 0.5 за 30 дней.
Фразы в кавычках — ×2 вес. Пустой запрос — хронологический порядок (как сейчас).

## Риски

| Риск | Митигция |
|---|---|
| Расхождение объединённого парсера с двумя старыми | тест-эквивалентность на золотых фиксах |
| Рост кэша | кап текста 4КБ/юнит; размер кэша в выводе `/recall stats` (будущее) |
| Гонки записи | tmp+rename, last-writer-wins — кэш восстанавливаем пересбором |
| Битый кэш | версионирование + полный ребилд |
