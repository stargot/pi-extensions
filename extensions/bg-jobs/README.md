# bg-jobs

Фоновые shell-джобы для pi (Windows 11 + pwsh): долгие команды — dev-серверы,
watch'и, миграции, длинные тесты — запускаются в фоне и не блокируют ход
сессии. Модель и пользователь получают мгновенный `id` + путь к durable-логу,
уведомление о терминальном состоянии, а модельные запуски — ещё и follow-up ход
с кратким итогом (exit code + хвост ≤ 2К + путь к полному логу).

Вдохновлено контуром `process` пакета
[pi-background-tasks](https://www.npmjs.com/package/pi-background-tasks),
урезано до нужного и переложено на конвенции пакета. Спека:
[docs/specs/2026-10-01-bg-shell-jobs-spec.md](../../docs/specs/2026-10-01-bg-shell-jobs-spec.md).

## Инструменты и команды

| Поверхность | Что делает |
|---|---|
| `bg_run` | Запустить команду в фоне: сразу `{ id, outputPath, pid }`; `wake: true` (по умолчанию) — по завершении придёт steer-ход с итогом; `timeoutSeconds` — kill по таймауту; `surviveExit` — пережить выход pi |
| `bg_status` | Статус всех джобов или одного (`id?`): id, статус, имя, started/ended, exit code, путь к логу |
| `bg_logs` | Хвост durable-лога (`tailChars`, по умолчанию 4096, максимум 65536) с честным маркером усечения и общим размером |
| `bg_kill` | Убить джоб: terminate всего дерева процессов (npm-обёртки и внучатые включительно), статус `killed` |
| `/bg [--survive-exit] [name] :: <command>` | Запуск с клавиатуры (origin `user`, wake всегда выключен): `/bg dev :: npm run dev`. Имя отделяется только ` :: ` с пробелами вокруг — голое `::` не режется (PowerShell-синтаксис вроде `[math]::Round(3.7)` остаётся командой целиком); без ` :: ` вся строка — команда, имя автогенерируется |
| `/jobs` | Таблица джобов (id, статус, имя, elapsed) |
| `/logs <id> [chars]` | Хвост лога в уведомление |
| `/kill <id>` | Kill с подтверждением `ctx.ui.confirm` |

Все тула — прямого доступа; `bg_run`/`bg_kill` несут `destructiveHint` для
аппрувал-политик (собственного confirm в туле нет — политика аппрувлов pi).
Ошибки (нет такого id, уже завершён) — броском с перечнем живых id.

## Как это работает

```
модель ── bg_run ──┐                     пользователь ── /bg ──┐
                   ▼                                            ▼
            ┌─────────────── Registry (.pi/jobs/jobs.json) ◄────┐
            │  id → {command, pid, status, outputPath, …}       │
            └───────┬───────────────────────────────────────────┘
                    │ spawn (pwsh -NoProfile, hidden console, stdout→file)
                    ▼
            Runner: процесс ОС (дерево через shared/proctree) + watcher (тик 1 c)
                    │                                 │
                    ▼ терминальное состояние          ▼ хвост лога
            notify (пользователь)          follow-up ход (модель)
                    └────────────┬────────────────────────┘
                                 ▼
                 widget (setWidget) + session-trace артефакт
```

Ключевой принцип: **рантайм расширения — не владелец процессов**. Джобы
спавнятся как независимые процессы, всё состояние живёт в реестре на диске —
`.pi/jobs/jobs.json` в проекте + `.pi/jobs/<id>/output.log` на каждый джоб.
Watcher тикает раз в секунду (таймауты, PID-опрос усыновлённых джобов);
после `/reload`, краша watcher'а или рестарта pi картина восстанавливается из
реестра + PID-проверок.

- **Обёртка команды:** `pwsh -NoProfile -NonInteractive -Command "<UTF-8
  encoding>; <команда>; exit $LASTEXITCODE"` — кодировка против кракозябр,
  проброс exit code нативных команд, `-NonInteractive` вместо вечного зависания
  на невидимом промпте.
- **Kill дерева:** `extensions/shared/proctree.ts` (`taskkill /T /F`) — тот же
  проверенный механизм, что у `subagents`; убивает npm-обёртки и внучатые
  процессы (покрыто тестом «cmd → pwsh внук умирает с деревом»). Перед kill'ом
  сверяется имя образа процесса (`Get-CimInstance`, ожидаем pwsh): мёртвый PID —
  джоб просто финализируется, живой чужой PID (переиспользование) — джоб
  помечается `orphaned`, чужое дерево не трогается.
- **Доставка итога:** модельные джобы (`bg_run`, `wake: true` по умолчанию) —
  `pi.sendMessage(..., { triggerTurn: true, deliverAs: "steer" })` — тот же
  механизм, что у `subagents`; пользовательские и `wake: false` — только
  `ctx.ui.notify`. Анти-спам: ничего не будится повторно, transition
  идемпотентен (kill-путь и exit-событие не задваивают доставку).
- **Реестр:** атомарная запись tmp+rename, мьютекс модуля на read-modify-write
  (параллельные `bg_run` из одного сообщения не теряют записи), id (8 hex)
  генерируется и вставляется в реестр ДО спавна. При первом старте
  `.pi/jobs/` добавляется в `.git/info/exclude` — пользовательский
  `.gitignore` не трогается.
- **Жизненный цикл:** `session_start` — PID-проверка running-джобов (мёртв PID
  без `endedAt` → `orphaned` + notify), монтаж виджета; `session_shutdown` —
  при выходе pi (`quit`) идемпотентный kill всех running, кроме
  `surviveExit` (те остаются сиротами со статусом `orphaned` и записью PID;
  при следующем `session_start` живой pwsh-сирота воскресает в `running`,
  watcher подхватывает). `/reload`, `/new`, resume и fork джобы НЕ убивают —
  новый экземпляр подхватывает реестр по PID. Wake-гвард по `sessionId`:
  модельный джоб, доживший до новой сессии (перезапуск pi), доставляет итог
  только `ctx.ui.notify` — steer в чужую сессию не уходит.
- **Виджет:** `ctx.ui.setWidget()` — `bg 2 running · 1 done` плюс имена
  running и свежие терминальные события; показывается, пока есть живые джобы
  или непрочитанные терминальные события, гаснет после `/jobs` / `bg_status` /
  `/logs`. Wake-доставленные итоги «непрочитанными» не считаются — они уже
  показаны в диалоге.
- **session-trace:** по каждому терминальному состоянию — запись
  `session-trace:bg-jobs` (id, имя, статус, длительность, exit code,
  путь к логу) по образцу `session-trace:subagents`.
- **Режимы:** виджет гвардится `ctx.mode === "tui"`; в RPC/print/JSON режимах
  работают инструменты, реестр и файлы (UI-пути либо но-op, либо просят TUI).

## Файлы

| Файл | Роль |
|---|---|
| `index.ts` | Фабрика: 4 тула, 4 команды, виджет, session-хуки, доставка итога |
| `registry.ts` | `jobs.json`: tmp+rename, мьютекс записи, переходы состояний, id-генерация, git-exclude |
| `runner.ts` | pwsh-обёртка, спавн в durable-лог, PID-живость, таймауты, хвосты лога |
| `format.ts` | Усечение хвостов с маркером, elapsed, статусы, таблица `/jobs` |

## Тесты

```bash
node --test extensions/bg-jobs/test/*.test.ts
```

Юнит: registry (гонки/merge/идемпотентные переходы/git-exclude), runner
(pwsh-обёртка, фикстуры echo/exit-code/sleep+kill, усечение хвостов), format
(таблица, elapsed, маркер). Интеграционные (с фейковым pi API): полный цикл
джоба, доставка steer/notify, kill дерева с внуком, усыновление реестра,
reload vs quit, таймаут. Ноль внешних сервисов и сети; спавн-фикстуры требуют
pwsh и на прочих платформах скипаются.

## Ограничения

- **БЕЗ песочницы — прямым текстом:** команда исполняется как локальный
  процесс с правами пользователя и его доступами; изоляции нет. Уровень
  доверия — как у обычного shell-тула pi; `bg_run`/`bg_kill` помечены
  `destructiveHint`, аппрувал-политика — не здешняя забота.
- **Kill дерева — `taskkill /T /F`, не Job Object:** снапшот дерева на момент
  kill'а; дрейф цепочек cmd/npm (внучатый процесс, переживший смерть родителя)
  — принятый риск v1 (ADR-6, отклонение 1 в спеке). Job Object требует
  нативного кода и держащего handle, конфликтующего с переживанием `/reload`.
- **Cap лога не введён (v1):** полный stdout/stderr пишется на диск без
  усечения — размер ограничивает сам пользователь; следите за бесконечно
  пишущими командами (`tail -f`, watch'и с болтовней).
- **Переживание закрытия терминала:** джобы переживают выход pi и `/reload`,
  но привязаны к консоли терминала — закрытие окна терминала убьёт их (в том
  числе `surviveExit`-сирот). Долгоживущие `surviveExit`-джобы имеет смысл
  держать в терминале, который не закрывается.
- **Windows-first:** kill дерева и спавн рассчитаны на Windows + pwsh;
  POSIX-ветка kill-дерева в `shared/proctree.ts` — заглушка (`TODO(posix)`).
- **Виджет пассивный (v1):** без интерактивного dock — навигация через
  `/jobs` / `/logs` / `/kill`.
- **Не-UTF8 вывод повреждается при чтении лога:** лог читается как UTF-8;
  нативные тулы, игнорирующие установленную обёрткой UTF-8-кодировку и
  пишущие в своей кодовой странице (cp866, 1251), оставляют в логе байты,
  которые при чтении хвоста превращаются в U+FFFD — «полный лог в файле» это
  не спасает, файл содержит сырые байты. Большинство dev-тулов отдают UTF-8,
  так что на практике проблема редкая.
