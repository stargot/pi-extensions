# prime-protocol — протокол оркестратора для pi

Каждая основная сессия pi работает как **prime** — оркестратор, который решает
задачу через рой субагентов, а не в одиночку. Расширение состоит из трёх
частей, работающих на одних и тех же guard'ах: не-armed сессия не инжектится
и не блокируется.

Порт локального расширения `~/.pi/agent/extensions/prime-protocol.ts`;
изменения поведения относительно исходника описаны в конце.

## Часть 1 — протокол (инжект системного промпта)

В `before_agent_start` к системному промпту основной сессии добавляется
протокол, собранный из одного источника истины — пула агентов
(`~/.pi/agent/agents/`):

1. **Тело `agents/prime.md`** (frontmatter срезается) — интро (первые строки),
   prime directive, жёсткие правила, контракт делегирования, обработка
   результатов, стоп-условия, формат отчёта;
2. **Бюджетная строка solo-правила** — рендерится из констант кода
   (`BASE_LOOKUP_ALLOWANCE`, `PER_DISPATCH_ALLOWANCE`, `FILE_TURN_LIMIT`),
   поэтому числа в промпте всегда совпадают с тем, что реально блокируют
   инструменты;
3. **Dispatch-таблица** (`| Role | Purpose | Model |`) — генерируется в момент
   инжекта сканом `agents/*.md`: каждый файл роли, кроме самого prime,
   отсортированный по имени; строка заполняется из `description` и `model`
   самого файла роли. Роль выходит из таблицы флагом **`dispatch: false`** в
   frontmatter. Добавление, удаление или смена модели роли обновляет протокол
   на следующей сессии — hand-maintained список, который может разъехаться,
   отсутствует по построению.

Инжект идёт только основным сессиям. Дети-субагенты протокол НЕ получают:
разведчик, которому вменено делегировать, перестаёт делать работу. Инжект
пропускается, когда процесс — ребёнок (см. «child-detect» ниже). Нет файла
`prime.md` — часть 1 no-op; пустой пул (нет подходящих агентов) убирает
таблицу.

## Часть 2 — dashboard (только TUI)

- первое сообщение пользователя сессии — notify-баннер (модель, размер пула);
- виджет `prime-status` под полем ввода живёт в реальном времени: solo
  лукапы/редакты против отправленных агентов по именам и количеству,
  остаток enforcement-бюджета хода. Чистые факты для человека.

## Часть 3 — solo enforcement (код, а не промпт)

Промпт-лимиты оказались неисполнимыми: живые сессии делали 40+ solo-лукапов
с инжектированным протоколом и нулевыми диспатчами. Теперь лимитируют сами
инструменты:

- лукапы ориентации (`read`/`grep`/`find`/`ls`/`glob` и читающие shell-команды)
  блокируются после `BASE_LOOKUP_ALLOWANCE` (3) за ход пользователя + по
  `PER_DISPATCH_ALLOWANCE` (3) за каждого отправленного агента (верификация
  его отчёта). Повторное чтение уже прочитанного файла бюджет не тратит.
  Надбавка начисляется после успешного спавна (`tool_result` без ошибки), шаги
  `task_batch` в режиме `chain` считаются так же, как `tasks`. Читающей
  считается каждая команда последовательности (`;`, `&&`, `||`), кроме
  потребителей пайпа (`npm test | tail` — не лукап); в списке также `sed`,
  `awk`, `findstr` и читающие `git show/log/diff/grep/blame`;
- правки более `FILE_TURN_LIMIT` (3) различных файлов за ход блокируются —
  массовая работа с файлами принадлежит воркеру. Shell-записи (редиректы
  `>`/`>>`, `Set-Content`/`Add-Content`/`Out-File`/`tee`) идут в тот же лимит;
  `/solo off` снимает и его;
- `/solo <N>` поднимает лукап-кап на ход, `/solo off` выключает enforcement
  до следующего сообщения пользователя;
- счётчики сбрасываются на каждом сообщении пользователя; дети
  (`PI_SUBAGENT_SESSION`) и не-armed сессии не блокируются никогда.

Блокировки объясняют причину и выход: отправить scout/task_batch, верифицировать
отчёт, или `/solo`.

## Child-detect — как распознаётся ребёнок

1. Дети панелей (subagents) запускаются с `PI_SUBAGENT_SESSION` в окружении;
2. headless-дети (task_batch) получают identity агента через
   `--append-system-prompt` → `systemPromptOptions.appendSystemPrompt`. Этот
   append сверяется с телами `agents/*.md` — совпадение значит child identity →
   пропуск. Любой другой append (например, пользовательский глобальный
   APPEND_SYSTEM.md) сигналом ребёнка не является: сессия остаётся armed,
   протокол инжектится вместе с ним. Сверка «любой непустой append» молча
   разоружала каждую основную сессию с APPEND_SYSTEM.md;
3. tool-allowlist дети не имеют инструмента `subagent` вовсе → `selectedTools`.

## Отличия от локального исходника

- **AUTOpool вместо списка из frontmatter**: таблица генерируется сканом
  каталога агентов, а не из списка `subagents:` в `agents/prime.md`; роль
  исключается флагом `dispatch: false` (ключ добавлен в известные ключи
  парсера subagents, чтобы не считать его неизвестным);
- **PRIME.md не читается**: интро — первые строки тела `agents/prime.md`,
  отдельный файл-манифест из цепочки инжекта убран;
- **бюджетная строка генерируется из констант кода**, а не живёт текстом в
  промпте-исходнике.

Чистая логика (frontmatter, dispatch-таргеты, рендер таблицы и бюджетной
строки, сверка тел агентов, классификация tool-input) вынесена в
зависимость-свободный `protocol.ts` — тесты гоняются без pi.
