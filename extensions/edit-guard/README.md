# edit-guard

Страховка инструмента edit. Модель присылает `edits[].oldText` как «точный» текст, и он регулярно не совпадает с файлом байт-в-байт. Часть расхождений встроенный edit прощает сам: BOM он срезает (`splitBom`), CRLF/LF нормализует (`normalizeToLF`/`restoreLineEndings`), типографику — умные кавычки, тире, юникод-пробелы — прощает через `normalizeForFuzzyMatch`. Уникальная ценность гарда — то, чего у встроенного edit нет:

- **indent-фаза** — правка с промахнувшимся отступом (табы vs пробелы, лишние ведущие пробелы) проходит вместо «oldText not found»;
- **пороговый fuzzy** — лёгкий дрейф текста спасается по консервативным построчным порогам, а не «нашёл что-то похожее»;
- **анти-неоднозначность** — если нормализованное совпадение есть в нескольких *разных* сырых местах, вызов блокируется: неизвестно, какое имелось в виду;
- **block-диагностика** — вместо общего «Could not find the exact text» модель получает строку файла, похожесть, диапазон и сниппеты ближайшего кандидата;
- **телеметрия** — каждое вмешательство остаётся в сессии как запись `edit-guard` (в контекст модели не попадает).

С гардом правка либо спасается, либо блокируется с объяснением — вслепую не применяется.

Расширение вешается на событие `tool_call` инструмента `edit`, читает целевой файл и прогоняет каждый `oldText` через `resolveEdit` — поиск по фазам возрастающей свободы:

| Фаза | Method | Что допускает |
|---|---|---|
| A | `exact` | точное вхождение — не вмешиваемся |
| B | `whitespace` | разница хвостовых пробелов; типографика (та же карта, что у встроенного edit, без NFKC — она меняет длины и ломает перенос смещений в сырой текст); однострочный needle ищется и внутри строки |
| C | `indent` | расхождение в ведущих пробелах/табах (табы vs пробелы), при равенстве числа строк |
| D | `fuzzy` | лёгкий дрейф текста: средняя посимвольная похожесть по строкам ≥ **0.85** и худшая строка ≥ **0.6** |

Разницу BOM и CRLF/LF/CR фаза B тоже видит (needle с `\n` против файла с `\r\n` восстанавливается в сырую подстроку с родным EOL), но это подстраховка: встроенный edit эти расхождения и так прощает сам.

Два порога нужны вместе: средняя пропускает одну испорченную строку в большом окне, нижняя граница на строку отсекает окна, где хотя бы одна строка разъехалась целиком. Перед fuzzy-фазой — prefilter: первые непустые строки окна и needle должны быть похожи хотя бы на 0.5, иначе окно даже не оценивается. Цена DP квадратична по длине строки, поэтому перед каждой парой строк срезается общий префикс/суффикс (суффикс-дрейф длинных строк сводится к тривиальному DP), а пары, всё ещё длиннее **4096** символов после среза, дисквалифицируют окно — лучше блокировка с диагностикой, чем минутное синхронное зависание edit-пути. Файлы длиннее 20000 строк fuzzy-фазу пропускают (дорого), фазы A–C работают.

## Что происходит при совпадении

- **exact** — вход не трогается, edit выполняется как обычно.
- **recovered** (`whitespace`/`indent`/`fuzzy`) — `edits[i].oldText` подменяется на точную сырую подстроку файла, где нашлось совпадение. Встроенный edit после этого совпадает байт-в-байт и режет ровно найденный диапазон. `newText` не трогается.
- **not-found** — похожесть ниже порога или найдено несколько *разных* сырых кандидатов (неоднозначность). Весь вызов блокируется: в `reason` перечисляются спасённые индексы, ненайденные правки со строкой файла, похожестью, «ближайшим кандидатом» (диапазон строк + сниппеты до 3 строк, обрезка 200 символов) и просьбой перечитать файл.

## Гарантии и границы

- `newText` никогда не изменяется — правится только то, **что** заменять, не **чем**.
- Файл не читается (нет/нет прав) — расширение молча пропускает вызов, edit сам выдаст свою ошибку.
- Не-edit инструменты отсекаются до какой-либо работы.
- `actual` — всегда сырая подстрока файла, поэтому после подмены edit применяется детерминированно; ошибиться «не в том месте» он не может. Риск только один: fuzzy-фаза может счесть похожим кусок, который автор правки имел в виду чуть иначе, — поэтому пороги консервативные, а всё, что надёжнее «точного совпадения после нормализаций», блокируется.
- Смешанные EOL в recovered-подстроке возможны (файл мог быть собран из кусков) — осознанно: подменяем ровно на то, что в файле.
- Побочный эффект блокировки: патчи уже спасённых правок к этому моменту вшиты в `input.edits` вызова. Это безвредно — заблокированный ввод выбрасывается, инструмент его не видит.
- Хендлер не бросает исключений: сбой внутри гарда (а `emitToolCall` pi их не ловит — упавший extension сломал бы сам edit) пишет телеметрию `action: "error"` и пропускает вызов.
- Телеметрия: одна запись `edit-guard` на вызов edit — `{ path, action: "pass" | "patched" | "blocked" | "error", edits: [{ index, method, similarity }], reason? | error? }` в сессию (в контекст модели не попадает).
